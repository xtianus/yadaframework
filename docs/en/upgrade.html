Changes in 0.7.9

Embedded database

Yada no longer attaches silently to any database that answers on the configured embedded port: the running server must use the configured data folder, otherwise the application fails at startup. If you rely on a database started separately on that port, configure the same datadir or a different port. On Linux and macOS, embedded database folders containing whitespace are refused at startup with a clear message.

Hibernate dialect

Hibernate still detects the dialect by itself, except when the embedded database is enabled: Yada then uses MariaDBDialect, because Hibernate can’t recognize MariaDB 11 through MySQL Connector/J and would fail at startup. The new <database><dialect> setting forces any dialect, e.g. MariaDBDialect for a MariaDB server reached through MySQL Connector/J. See Hibernate Dialect.

Sorting

A single sort=property,direction request parameter bound to YadaPageRequest works: it was split at the comma by Spring and rejected with "No sort column specified".

Security hardening

The following changes come from a security review of the framework. Some of them break existing code or configuration: read the whole section before upgrading an application that uses Yada security, DataTables or uploads. Unless stated otherwise there are no new mandatory configuration keys.

Security links are single-use bearer tokens

Autologin, registration confirmation, password recovery and email change links no longer carry a number that is stored in the database. A link now has the form <id>-<64 hex characters>; the hex part is a random 256-bit secret that exists only in the link, while the database stores a SHA-256 digest of it (column tokenHash). A link is a bearer token, not a signed link: whoever holds it can use it once, until it expires. Opening a link consumes it under a database row lock, so two concurrent requests can’t both succeed, and a rolled-back change leaves the link usable.

  • Registration confirmation links expire after security/registration/expirationHours (default 24), password recovery and email change links after security/passwordReset/expirationMinutes and security/emailChange/expirationMinutes (default 30 each). security/autologinExpirationHours (default 10) is unchanged, but an autologin token without expiration is now invalid.

  • Links can be built only from the instance returned when the token is issued (YadaTokenHandler.makeAutoLoginToken, YadaRegistrationRequestDao.issue). Building a link from a token loaded from the database throws YadaInvalidUsageException: issue a new token instead.

  • Removed: YadaRegistrationRequest.getToken/setToken, YadaAutoLoginToken.getToken/setToken, YadaTokenHandler.makeLink(long, long, Map), YadaRegistrationRequestDao.findByIdAndTokenOrderByTimestampDesc and YadaAutoLoginTokenDao.findByIdAndTokenOrderByTimestampDesc. YadaTokenHandler.parseLink now returns a YadaSecurityTokenCodec.ParsedSecurityToken, or null when the link is not valid.

  • New: YadaSecurityTokenCodec, YadaAutoLoginTokenDao.issue/findValid/consume, YadaRegistrationRequestDao.issue/findValid/consume/findByUserAndRegistrationType/getLifetimeMillis and YadaRegistrationController.handleEmailChangeRequest. YadaRegistrationRequestDao.save is deprecated: it issues new requests and throws for an existing one; YadaAutoLoginTokenDao.save throws for a new token. Applications that create EMAIL_CHANGE requests themselves keep working through save, or can use handleEmailChangeRequest.

  • The action of an autologin link must be a local path accepted unchanged by YadaWebUtil.safeLocalRedirect (see below), otherwise makeAutologinLink throws. The action is decoded once, by Spring MVC: callers that encoded it twice must encode it once.

  • A registration confirmation that finds an existing user, and the USER_EXISTS and ERROR outcomes of changeUsername, now consume the request. YadaAutoLoginTokenDao.deleteExpired also deletes tokens without expiration, and findByYadaUserCredentials excludes them. The new YadaLogRedaction class hides token secrets in logged text (see Logging below).

Autologin needs a confirmation click

GET /autologin/{token} no longer logs in: it shows a confirmation page (/yada/security/autologinConfirm) with the account name and a button, and only the POST to the same url, protected by CSRF, consumes the token and logs in. This stops mail scanners and link previews from using the link. The page can’t be disabled. A user who is already logged in is never switched to another account, and the token stays unused. The CSRF token is renewed after the login. Disabled users are rejected. The page texts are the message keys yada.autologin.confirm.title, .message, .button and .cancel; English defaults are built in, so applications only define them to translate or reword. If the application sets its own CsrfTokenRepository, expose it as a bean so that the login can renew its token.

Database migration and rollout

Applications that map YadaRegistrationRequest or YadaAutoLoginToken need a Flyway migration, with the next free version number, for example V<n>__hashed_security_tokens.sql. It must:

  1. delete the rows of every JOINED subclass of YadaRegistrationRequest and YadaAutoLoginToken, then the rows of the two tables themselves, because outstanding links can’t be converted;

  2. drop the token column of both tables, and add the tokenHash varchar(64) not null column to both and the expiration TIMESTAMP NULL column to YadaRegistrationRequest;

  3. when the schema still has the old unique constraints on yadaUserCredentials_id (both tables) or trattamentoDati_id (YadaRegistrationRequest), first add a plain index on each of those columns, in its own ALTER, then drop the unique index (SHOW INDEX FROM YadaAutoLoginToken shows the names). A user can now hold several tokens.

The complete script, with a comment on each step, is YadaExamples/src/main/resources/database/V002hashed_security_tokens.sql (YexRegistrationRequest is the example subclass); YadaTests/src/main/resources/database/V002hashed_security_tokens.sql is the same for the test application. Check the result against the schema generated for your entities.

Roll out in a maintenance window:

  • stop every node of the old application before the migration runs, so that no node issues a legacy token meanwhile, then start the new version;

  • every outstanding autologin, registration, password recovery and email change link stops working: users have to ask for new ones. Accounts and profiles are not touched;

  • DDL is not transactional in MySQL and MariaDB: back up the token tables (and the subclass tables) first. A failure after the DELETE statements can’t be rolled back by Flyway: fix the script and run repair, or restore the backup;

  • rolling the application back needs a restore of the old schema; the old links are gone either way.

Registration binding and password reset

The registration request and the password reset form are bound from user input, so they are restricted to what the form needs.

  • YadaRegistrationController.handleRegistrationRequest throws YadaInvalidUsageException for a request that already has an id or a user. The application controller that binds the registration form must declare an @InitBinder for its model attribute that calls the static YadaRegistrationController.setRegistrationAllowedFields(binder, "extraField", …​): only email, password and confirmPassword plus the listed subclass fields are bound.

  • /yadaPasswordResetPost binds the new class YadaPasswordResetForm, which has the email field only. The application page that shows the form should use th:object="${yadaPasswordResetForm}" and a YadaPasswordResetForm method parameter instead of YadaRegistrationRequest. The email is stored trimmed and lowercased, and the answer is the same whether the user exists or not.

DataTables query policy

DataTables requests are sent by the browser and can be tampered with. Every query now runs inside a server-side YadaDataTableQueryPolicy, which lists the entity paths a table may return, search and sort. See Java Ajax Endpoint.

  • Removed: YadaDataTableDao.getConvertedJsonPage(YadaDatatablesRequest, Class, Locale). Custom endpoints must pass a policy with getConvertedJsonPage(request, MyEntity.class, locale, POLICY), built with YadaDataTableQueryPolicy.forEntity(…​), or take it from a table configured in Java with yadaDataTableFactory.getSingleton(tableId, locale).getQueryPolicy(). A request for anything outside the policy is rejected with yadaError and no data, so a missing column shows up as an empty table.

  • Removed: the deprecated YadaDataTableDao.getJsonPage(…​), which serialized whole entities. The protected getPage(…​) takes the resolved policy. YadaDatatablesRequest.addExtraJsonAttribute is deprecated: declare extraOutput(path) in the policy: extras are returned on every row, and a requested extra that the policy does not declare rejects the request.

  • The default /yadaDataTableData endpoint needs no code change: it derives the policy from the column definitions. A column that is not a persistent field of the dtEntityClass() class (a getter, a computed value, an attribute that exists only in a subclass) becomes output-only: it is still shown but never searched or sorted, a sort request on it is rejected, and one warning is logged per table and column. Set the subclass as dtEntityClass() to search or sort on it. Columns are searchable and orderable unless dtSearchableOff() or dtOrderableOff() is set.

  • With an explicit forEntity policy, a searchable or orderable path that is not a persistent field fails in build(): declare getters and computed values with column(path, false, false), and build the policy for the concrete subclass when the table shows subclass attributes: a subclass-only path is refused on a policy for the superclass, even as output-only.

  • Columns that would return a credential (password, token, tokenHash, secret, salt…​ in any path segment, map keys included), a whole entity or an embeddable are refused, and entity toString() values are never returned. An embeddable value reached through a getter is emitted as null.

  • Order directions other than asc and desc and invalid order indexes are rejected, dataTableId must match [A-Za-z0-9_-]{1,100}, and map keys in paths (name.en) are bound as query parameters of the map key type instead of quoted literals.

Client address and trusted proxies

YadaWebUtil.getClientAddress(), the deprecated getClientIp() and the remoteIp field written by AuditFilter now return request.getRemoteAddr(), unless the peer is a trusted proxy: a client can no longer choose the address in the audit log by sending an X-Forwarded-For header. getClientIp() no longer returns the [for …​] text; the sanitized raw header is in the new MDC key forwardedFor, which can be added to logback patterns as %X{forwardedFor}.

  • Behind a reverse proxy the preferred setup is Tomcat’s RemoteIpValve with remoteIpHeader="X-Forwarded-For", with internalProxies and trustedProxies listing exactly the addresses of the ingress (the Tomcat default for internalProxies covers every private network). The ingress must overwrite, not append to, the client-supplied X-Forwarded-For, X-Forwarded-Proto and X-Forwarded-Host, and Tomcat must be reachable only through the ingress. With the valve, leave the framework list empty.

  • Without a valve, the optional <security><trustedProxies><proxy>IP</proxy>…​</trustedProxies></security> configuration lists the proxies whose header is believed. Only IP addresses are accepted; *, names and ranges are ignored. The default is an empty list.

See Client address behind a reverse proxy.

Security headers, login failures and lockout

  • Applications extending YadaSecurityConfig send Spring Security’s default response headers again: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Cache-Control with Pragma and Expires that disable caching of dynamic responses, X-XSS-Protection: 0, and Strict-Transport-Security on HTTPS requests only, plus the new Referrer-Policy: same-origin. Resources served by the YadaWebConfig handlers keep their max-age. Applications that frame their own pages must call frameOptions(sameOrigin) in their subclass. Behind a TLS-terminating proxy HSTS is sent only if the request is seen as secure (RemoteIpValve), otherwise set it at the proxy. Applications that added these headers themselves may now send them twice and should remove their own.

  • An unknown username now sets the same passwordError request attribute as a wrong password, so the login form can’t be used to find out which accounts exist. usernameNotFound and the password request attribute are no longer set (REQUESTATTR_USERNAMENOTFOUNDFLAG and REQUESTATTR_PASSWORD are deprecated). Login templates should show one generic "invalid email or password" message for passwordError and must not use ${password}; the project template and the example modal are updated. The 401 fallback (no failure url) sends "Authentication Failed" without the exception message.

  • YadaUserDetailsService.loadUserByUsername signals a locked account with a locked UserDetails, so the authentication provider throws LockedException; it no longer throws TooManyFailedAttemptsException. Custom failure handlers that check for TooManyFailedAttemptsException must check LockedException too (the framework handler checks both). An unknown username also goes through incrementFailedAttempts, which updates no row.

Multipart forms and CSRF

  • The CSRF token is no longer added to the action url of multipart forms, where it ended up in logs, history and Referer headers. It is sent as the hidden _csrf field (added by th:action, and by yada:actionUpload for absolute local paths) or, for Ajax uploads, in the CSRF header from the _csrf and _csrf_header meta tags. A multipart form with a plain static action and no hidden _csrf field, which used to work thanks to the url token, now gets 403: use th:action or add the hidden input. A _csrf parameter written in a multipart action query is removed at render time. MultipartFilter must stay before the Spring Security filter.

  • yada:actionUpload adds the hidden token only when the action is an absolute local path accepted by YadaWebUtil.isSafeLocalRedirect (now public); relative paths and absolute urls, even of the same host, get no token and therefore a 403 on submit: templates must write the action as an absolute local path such as @{/…​}.

  • A plain (non-Ajax) multipart form larger than maxFileUploadSizeBytes no longer reaches the controller with limitExceeded(request) true: it gets HTTP 413 from YadaUploadLimitAccessDeniedHandler before any controller. Map 413 to an error page in web.xml for a friendly message, or upload with Ajax or check the size in the browser. Ajax uploads that send the CSRF header still reach the controller with limitExceeded true. An application with its own accessDeniedHandler gets 403 instead, unless it wraps its handler in YadaUploadLimitAccessDeniedHandler. If a subclass sets sessionManagement.invalidSessionUrl, a plain-form POST from a browser without a session is redirected there instead of getting 413. The browser sees the 413 only if Tomcat can swallow the rest of the body (maxSwallowSize, 2 MB by default): see CSRF token of multipart forms.

Error responses

  • Error pages and Ajax modals show the standard HTTP reason phrase instead of the exception or servlet error message. The global exception handler no longer puts e.getMessage() in errorDescription or yadaExceptionMessage; applications that showed it, for example during development, must read the server log. DataTables database failures answer with yadaError.error "Server error".

  • When the response is already committed, /yadaError and the global exception handler write nothing and return no view: the client sees a truncated or aborted response instead of a page that looks complete.

Local redirect targets

New YadaWebUtil.safeLocalRedirect(String) validates a redirect target that comes from the client, like a request parameter or a stored location: it returns the candidate unchanged only if it is an absolute local path such as /dashboard?tab=users#top (no //host, backslash, control character, . or .. segment, nor encoded separator, even when double-encoded), otherwise /. Use it as "redirect:" + yadaWebUtil.safeLocalRedirect(target). Never pass the result to redirectString, which encodes the path again and may prepend a second locale. isSafeLocalRedirect(String) returns whether the candidate would be returned unchanged.

Impersonation

  • yada.impersonate(url, userId, method) now sends currentLocation as location.pathname + location.search, not the absolute location.href. The value is a local path that includes the servlet context path and any locale segment, for example /shop/en/dashboard/user?page=2. A controller that saves it and later replays it must validate it with safeLocalRedirect when saving, remove the context path if the value starts with it ("redirect:" adds it again, otherwise a non-root application redirects to /ctx/ctx/…​), and replay it as "redirect:" + safeLocalRedirect(saved), never with redirectString. The example UserProfileController.contextRelativeLocation does exactly this.

  • yada.dataTableCrud extra buttons with ajax: false and a method other than GET now submit a POST with yada.postNavigate, in windowName when set. Before, method was ignored for non-Ajax buttons.

  • Impersonation and deimpersonation must be POST-only. In applications that copied the example UserProfileController: call yada.impersonate(…​, "POST"), use a th:action form for deimpersonation, and send "method": "POST" on legacy table buttons. The example ajaxAddOrUpdateUserProfile is POST-only and binds only allowlisted fields, ajaxEditUserProfileForm takes userProfileId, an unknown userProfileId fails instead of creating a user, and failedAttempts can only be reset to 0.

  • The project template header.html generated by YadaTools shows the impersonation banner as a POST form to /dashboard/user/deimpersonate; generated applications need a POST-only deimpersonation endpoint.

Logging

Token secrets are replaced by <id>-[hidden] in logged request urls, query strings and email bodies, and the token parameter is hidden by AuditFilter. Developers who used to copy links from the development log must use a mail catcher such as Mailpit. Spring and Hibernate DEBUG logging (for example org.springframework.web and org.hibernate.SQL) still prints complete request urls and bound values: keep it off in production. Server error details are only logged, never sent to the browser.

Embedded database installation

The installation step of the embedded MariaDB (mariadb-install-db) now runs with the configured embedded tmpDir on Linux and macOS, through the new public factory YadaMariaDB.newEmbeddedDB(DBConfiguration), which YadaMariaDBServer uses. MariaDB4j passed --tmpdir only to the server, so concurrent installations (parallel builds or tests) shared /tmp, deleted each other’s temporary tables and failed with "Unknown table 'mysql.tmp_user_sys'". As in MariaDB4j, a non-empty data folder is reused and not installed again. Windows is unchanged: the original MariaDB4j command runs with the system TEMP folder. YadaMariaDB copies the MariaDB4j install command: when upgrading MariaDB4j, compare createUnixInstallProcessBuilder() with the new DB.createDBInstallProcess().
