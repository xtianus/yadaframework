# Workspace Build Notes

## Gradle ownership and entry points

- The repository-root `settings.gradle` names the build `yadaframework` and includes exactly `YadaWeb`, `YadaWebSecurity`, `YadaWebCMS`, `YadaWebCommerce`, `YadaAi`, `YadaTools`, `YadaDocs`, and `YadaTests`. The root has no `build.gradle`; `YadaTests` contains a test application but is never packaged or published. `YadaBones` has no Gradle build script.
- There are two Gradle 8.14.3 wrapper installations: the repository root for framework work and `YadaExamples` for the independent example application. Framework modules have no settings or wrappers. Run `./gradlew test` or `./gradlew build` at the repository root, and use qualified tasks such as `:YadaTests:integrationTest` or `:YadaDocs:asciidoctor` to select a module. On Windows, use `gradlew.bat`.
- All framework tests live in `YadaTests` (see `yada_tests_notes.md`); the other modules have no test sources and their `test` tasks report `NO-SOURCE`. Root `./gradlew test`, `check` and `build` run only `:YadaTests:test`; the database, browser, tooling and documentation suites run only through explicit `:YadaTests:*` tasks, with `:YadaTests:frameworkCheck` as the full verification. No production module depends on `YadaTests`.
- `YadaExamples/settings.gradle` owns its application root and maps `YadaWeb`, `YadaWebSecurity`, `YadaWebCMS`, and `YadaWebCommerce` to sibling directories. Its schema and Sass paths are relative to that application root. External consumers such as `LumiligoSite` likewise keep their own roots and include framework sources through `projectDir` mappings.
- `shared.gradle.properties`, `loadSharedProperties.gradle`, and `eclipseSetup.gradle` live at the repository root. All eight build scripts apply the loader with `../loadSharedProperties.gradle`, and the loader reads `../shared.gradle.properties`, both relative to the applying project. Explicit loading keeps `yada_version` and `java_version` available under framework, example, and external-consumer settings. A sibling application cannot apply the loader directly, because `../shared.gradle.properties` would resolve next to the application; applications get the shared properties by including the framework modules.
- The published `net.yadaframework:yadatools:0.7.7.R4` plugin is on the `YadaExamples` buildscript classpath only; `YadaWeb` has no buildscript dependencies. Including the source `YadaTools` project cannot supply another project's buildscript classes. `YadaTools` SSH plugin 2.11.2 and `YadaExamples` SSH plugin 2.10.1 belong to separate builds.
- Unqualified root `publish` publishes six libraries. Tools publication tasks also depend on the web, security, CMS, and commerce publication tasks, producing five artifacts, including when invoked by `YadaTools - upload to public repo.launch`. AI is outside that tools publication graph.
- Dependabot scans `/` and `/YadaExamples` in one weekly Gradle update block. Root settings expose the eight framework build scripts; each build entry point exposes its own wrapper.
- There is no fixture dependency between modules: the test fixtures `YadaEmbeddedTomcatTestServer` and `YadaTestConfigurationScope` live in `YadaTests/src/harness/java/net/yadaframework/core`, and `YadaWeb` does not apply `java-test-fixtures`.
- `:YadaDocs:verifyAsciidoc` stages the documentation sources in `docsVerificationDir` (set by YadaTests to `YadaTests/build/docs-verification`), copies the docinfo header into each staged folder, renders HTML there with every Asciidoctor warning fatal, and checks relative links and anchors. It never writes into the source tree or `docs/`, unlike `copyDocInfoHeader`, `asciidoctor` and `asciidoctorPdf`.

## YadaExamples tests

- `bash YadaExamples/gradlew -p YadaExamples test` (also run by the example `check` and `build`) runs `YadaExamples/src/test`, the tests of the example application. They never use YadaTests or its harness; framework behavior is tested only in YadaTests. The task fails when it discovers no test (filtered runs excepted). The example build has no dependency lockfile.
- The task sets `yada.configurationFile` to `src/test/resources/yex-test-configuration.xml`, which replaces `configuration.xml`: it reads only the framework properties and `conf.webapp.test.xml` (no `/srv` file, no `conf.webapp.dev/tst/prod.xml`). That file repeats the application settings (roles, locales, entity package) and enables the framework embedded MariaDB with `databaseMigrationAtStartup`. `src/test/resources/logback-test.xml` keeps logging on the console, away from the `/srv` log files.
- `ExampleTestDatabase` sets `yex.test.runDir` (`build/test-db/<pid>`), `yex.test.databaseDir` (`<runDir>/db-<n>`) and `yex.test.databasePort` (a free port, never 3306 or 63306) before the configuration is read; `conf.webapp.test.xml` reads them with `${sys:...}`, which Commons Configuration resolves at each read. When MariaDB can't start because another process took the port, `TestRootConfig` creates the `yadaMariaDBServer` bean again with a new port and folder (up to 3 attempts; a failed start costs about 40 seconds, the MariaDB4j startup timeout). `java.io.tmpdir` is `build/tmp/test-jvm`.
- MariaDB4j stops the database process with its JVM shutdown hook; a test JVM killed with SIGKILL normally takes the process with it. Before deleting `build/test-db`, so that every migration runs on a fresh schema, the `test` task stops any process whose command line contains `mariadbd` and that folder. To clean up by hand, stop only `mariadbd` processes started from `YadaExamples/build/test-db` and delete that folder.
- The test environment is `tst` (not development): `YadaRegistrationController.handleRegistrationRequest` deletes the registration request when the email can't be sent, links in emails use the configured `http://localhost/` server address instead of the request, `YadaUserSetup` doesn't log passwords, and email subjects start with `[TST]`.
- Configuration overrides: `ExampleWebTestBase.overrideConfiguration("security/autologinExpirationHours", "1")` replaces `YadaConfiguration`'s configuration with an override layer on a fresh copy of the test configuration until the end of the test (several values replace a repeated element, `"x/@attr"` sets an attribute). It doesn't affect values cached by `YadaConfiguration` (environment, server addresses) or read by beans at startup; for those, `-PyexTestSettings=<file>` names an XML file (`<config>...</config>`) listed first in `yex-test-configuration.xml`, e.g. `<config><info><env>dev</env></info></config>` for a whole run in the development environment.
- `ExampleWebTestBase` boots the classes returned by the real `WebApplicationInitializer` (`TestRootConfig`, `TestServletConfig` in `net.yadaframework.example.core`, for access to its protected methods) in one cached `@ContextHierarchy` over `src/main/webapp`. `TestRootConfig` overrides the `javaMailSender` bean with an in-memory `CapturingMailSender`. MockMvc gets the filters of `SecurityWebApplicationInitializer` plus `springSecurity()`. MockMvc records forwards without executing them, so a locale path like `/en/dashboard` only returns its forwarded url: tests request paths without the locale.
- Before the first test of each class, `resetDatabase()` deletes every row except the Flyway history and recreates admin, supervisor, user and target accounts through `YadaUserCredentialsDao.create(..., UserProfile.class)`, as the example `Setup` does. `login(email, password)` posts the real login form and returns the authenticated `MockHttpSession`; `csrfToken(session)` gives the token after login.
- The application `run` task has no main class configured and fails with "No main class specified"; `classes` and `war` work.

## Eclipse metadata generation

- Eclipse metadata (`.project`, `.classpath`, `.settings/`) is git-ignored and regenerated from the chosen owning build. For framework work, run `./gradlew cleanEclipse` at the repository root, then `./gradlew eclipse` in a separate invocation. The generated security classpath references `/YadaWeb` without test code.
- Every framework Java module except `YadaDocs` applies the root `eclipseSetup.gradle` after `loadSharedProperties.gradle` (after `apply plugin: 'eclipse'` in `YadaTools`). `YadaDocs` has its own Eclipse setup; the example also keeps its own setup. The shared script defines Eclipse JDT compliance, the `JavaSE-<java_version>` JRE container, the WTP `jst.java` facet where WTP is applied, and the Buildship nature/builder, using `java_version` from root `shared.gradle.properties`. Its `.settings` paths resolve relative to each applying project.
- Gradle's `eclipse` tasks merge existing files. A stale `jst.java` facet can override JDT settings and downgrade the compiler and JRE container. `eclipseSetup.gradle` removes facets whose version differs from `java_version` and de-duplicates facets, natures, and build commands on merge.
- Buildship's *Refresh Gradle Project* does not run `eclipseWtpFacet`/`eclipseWtpComponent`, so it cannot repair a wrong facet version, and it skips projects lacking `org.eclipse.buildship.core.gradleprojectnature`. Run `cleanEclipse` followed by `eclipse` as separate invocations when metadata is inconsistent; task ordering within one invocation is not guaranteed.
- Buildship writes `.settings/org.eclipse.buildship.core.prefs`; Gradle's `cleanEclipse`/`eclipse` do not regenerate it. The required `connection.project.dir` is relative to the module directory: `..` for modules owned by the framework root, empty for the `YadaExamples` application root, and `../YadaExamples` for its framework modules. External applications use the relative path to their own root, such as `../../LumiligoSite` for framework modules owned by that application. Reimport through Buildship to establish these connections; do not commit generated preferences. A Buildship import over existing prefs files keeps their stale `connection.project.dir` and other values while reporting no problems, so to switch ownership, remove the projects from the workspace (keeping contents), delete every module's `org.eclipse.buildship.core.prefs`, then import the chosen root with *Existing Gradle Project*.
- Buildship stores one build connection per module directory. Simultaneous ownership of shared modules by the framework and example builds requires separate checkouts and separate Eclipse workspaces. Within one checkout, switch ownership by reimporting the chosen build.
- Buildship `GRADLE_DISTRIBUTION(WRAPPER)` launches resolve the build from their `working_dir`, not from the module's `connection.project.dir`: Gradle searches upward for the owning `settings.gradle` and Buildship uses that build's wrapper ("Gradle wrapper from target build"). A launch with `${workspace_loc:/YadaWeb}` therefore runs the root 8.14.3 wrapper and qualifies its tasks as `:YadaWeb:<task>`, so module `Launches` folders need no retargeting. The framework wrapper update launch runs the root `:wrapper` task from `${workspace_loc:/yadaframework}`.
- A running Eclipse keeps an already-loaded launch configuration in memory, so editing its `.launch` file on disk outside Eclipse does not change what *Run Configurations* executes. Edit launch arguments inside Eclipse; the console header line "Program Arguments" shows what is actually passed.

## Pinned library versions

- Spring Framework stays on 6.2.x and Spring Security on 6.5.x; Spring Security 7 requires Spring Framework 7.
- Thymeleaf (`thymeleaf-spring6`, `thymeleaf-extras-springsecurity6`) stays on 3.1.3. Since 3.1.4, template-name expressions inside fragment expressions run restricted and reject `@bean` references, which breaks the documented Yada pattern `~{${@yadaNotify.viewName} :: modal}` (also `@yadaWebUtil.modalConfirmViewName` and `@yadaWebUtil.getFormFragment(...)`). The failure depends on the SpEL expression cache, so it appears only on some requests. Upgrading requires replacing that pattern in framework views, docs and applications first.
- `vibur-dbcp` stays on 25.0 with `concurrentlinkedhashmap-lru` as its statement cache. 26.0 uses an optional Caffeine dependency for the cache, and when pool settings are invalid and connection tracking is enabled its `start()` calls `terminate()`, which throws a `NullPointerException` that hides the original `IllegalArgumentException`.
