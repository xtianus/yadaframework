# YadaTests Notes

`YadaTests` owns every automated test of the framework modules. `YadaTests/README.md` lists the suites and commands; `YadaTests/coverage-inventory.md` maps tests to suites and records known framework issues.

## Source sets and dependencies

- `src/main` is a small Spring MVC application in `net.yadaframework.tests` (configuration in `core`, scenario controllers in `web`, DAOs in `persistence.repository`, `TestDataService` and `StartupSchemaCheck` in `components`). It is never packaged: Tomcat mounts its compiled output and `src/main/webapp`.
- `src/harness` holds the test infrastructure and never depends on `src/main`: names of application classes are passed as strings or functions.
- `src/test` (unit), `src/integrationTest`, `src/e2eTest` (Playwright Java) and `src/toolTest` (YadaTools, TestKit) have separate classpaths. Ai and Tools stay out of the shared runtime classpaths. JUnit and Mockito versions come from the shared `testCommon` configuration; all configurations are locked in `gradle.lockfile` (refresh with `../gradlew :YadaTests:dependencies --write-locks`).
- Relocated tests keep their original packages, because some use package-private members (e.g. `YadaEmbeddedTomcatTestServer.resolveClasspathDirectories`).

## Harness

- `TestRun` creates `build/runs/<run-id>` with the MariaDB `MariaDB`, `data` and `tmp` folders, a free port (never 3306 or 63306), schema `yts_<run-id>`, and a generated `configuration.xml` that overrides the classpath `conf.webapp.yts.xml`. `close()` deletes the folder only when the port is free and fails if anything survives.
- `TestRun.setConfigurationValue(path, values...)` writes `conf.settings.xml`, the first (highest priority) source of `configuration.xml`. With the override combiner a repeated element given there replaces the whole list of the lower files, while single elements are merged with their siblings. Values are read at application start; `ApplicationSession.start(runConfigurer, seeder)` and `BrowserTestSupport.configureRun(TestRun)` apply them before startup.
- `LogCapture` attaches a logback `ListAppender` to the root logger; the application shares the test class loader, so its events are captured too.
- `TestApplication.start(run)` opens a `YadaTestConfigurationScope`, starts `YadaEmbeddedTomcatTestServer` with exactly `SecurityWebApplicationInitializer` and the application initializer, parent-first class loading, and the `globalInitializerClasses` parameter that installs `EmbeddedDatabaseOwnership`. That initializer swaps the class of the `yadaMariaDBServer` bean for `CapturingMariaDBServer`, which records itself in `OwnedDatabases` as soon as it is constructed, so a failed refresh can't lose the handle needed to stop the process. Startup is retried with a new port only when the database never started and the port is taken.
- Teardown order: Tomcat (contexts, EntityManagerFactory, pool), then `OwnedDatabases.stopAll()`, then the configuration scope.
- `YadaTestConfigurationScope` sets `yada.configurationFile`, clears `YadaAppConfig.CONFIG`, and on close stops the scoped reload trigger and restores the property, the static configuration and `YadaUtil.applicationContext`. Only one scope is active at a time.
- `YadaEmbeddedTomcatTestServer` either runs the initializers found in the mounted classpath roots (inferred from the nearest `build` ancestor of the webapp folder, or passed explicitly) or exactly an allowlist set with `setInitializerClassNames`. Tomcat does not throw when the web application fails to start, so `start()` checks the context state and reports the root context exception that Spring stored in the servlet context. It restores the JVM-wide `catalina.base` and `catalina.home` properties on close. Before starting Tomcat it initializes Thymeleaf's `SPELVariableExpressionEvaluator` with the parent class loader as context class loader: that class captures the context class loader once per JVM for its compiling SpEL parser, and a captured web application loader would make every later SpEL compilation fail with `NoClassDefFoundError: .../CompiledExpression` after that application is closed (`SpelCompilerAcrossApplicationsTest`). Its default base folder is under `build/tomcat` when the `yts.buildDir` property is set.
- `YadaMariaDBServer` installs a new database with `YadaMariaDB.newEmbeddedDB`, which passes the configured embedded `tmpDir` to `mariadb-install-db` as `--tmpdir` (MariaDB4j passes it only to the server). mariadbd deletes every `#sql*` file of its tmpdir at startup and the installation keeps temporary tables there, so installations sharing `/tmp` can break each other ("ERROR: 1051 Unknown table 'mysql.tmp_user_sys'"); `EmbeddedDatabaseInstallTmpDirTest` checks it. MariaDB4j's default socket is still `java.io.tmpdir/MariaDB4j.<port>.sock`, unique per port.
- `DatabaseFixtures.reset()` deletes the rows of every table except the Flyway history with foreign key checks disabled and resets the auto-increment counters (DELETE, not TRUNCATE: TRUNCATE is DDL in MariaDB and once hit a lock wait timeout), then runs the seeder (`TestDataService::seedDefaults`), so default rows get the same ids every time. `ApplicationSession` bundles a run, its application and fixtures.
- `BrowserTestSupport` (e2e) starts one application and one Chromium per class, a new browser context and a database reset per test, and writes a screenshot and trace for failed tests to `build/e2e-artifacts`.

## Application facts

- The application database schema comes from Flyway `V001__baseline.sql` plus later migrations (`V002__hashed_security_tokens.sql`); V001 was generated with `:YadaTests:dbSchema` from `src/dbSchema/META-INF/persistence.xml` (MariaDB dialect, script only). `StartupSchemaCheck` fails the root context when V001 is not in the history as a successful SQL migration.
- `:YadaTests:webTestDbSchema` generates the historical YadaWeb core test schema (`YadaWeb/schema/V1__yadatest.sql`) from `src/webTestDbSchema`; `YadaWeb:testDbSchema` only points to it.
- `YadaJpaConfig.chooseDialect` sets the Hibernate dialect: the configured `<database><dialect>`, else `MariaDBDialect` when the embedded database is enabled (MariaDB 11.4 through MySQL Connector/J can't be detected), else none, so Hibernate detects it (`MySQLDialect` for MySQL). The YadaTests application relies on the embedded default.
- Framework resources under `/yadares` are reached through `yada:src`/`yada:href`, which add the framework version required by the resource handler. jQuery and Bootstrap are served locally from `src/main/webapp/static`.
- Email is enabled with `CapturingMailSender` (a `JavaMailSenderImpl` whose `doSend` stores `CapturedMail` records) as the `javaMailSender` bean; `TestDataService.seedDefaults()` empties it, so every reset starts with an empty mailbox. `TestRun` writes no `<email>` section. The email templates are in `src/main/resources/template/email` and `<email><logoImage>` must point to an existing classpath resource, because `YadaSecurityEmailService.sendPasswordRecovery` always adds the logo as inline resource.
- `RegistrationController` wires `YadaRegistrationController` as YadaExamples does, with an `@InitBinder` allowlist on the registration request; `net.yadaframework.tests.web.security.auth.EmailChangeScenarioController` provides the email change flow; the framework `yadaPasswordResetPost` redirects to `<security><passwordReset><passwordResetSent>` (default `/`), and `HomeController` passes the flash attributes of `/` on to `/test/home` so that notifications survive the second redirect.
- Links built with `YadaConfiguration.getServerAddress()` use the configured `http://localhost/` (no port), while links built from the request in the dev environment carry the Tomcat port; `getServerAddress(request)` caches its value in the same field. Tests use only the path and query of emailed links.
- The `entityManager` bean of `YadaJpaConfig` is not bound to Spring transactions; transactional test code uses `SharedEntityManagerCreator` or the application DAOs.
- The DataTables scenario (`net.yadaframework.tests.web.datatable`, page `/test/admin/datatable/users`) configures `ytsUserTable` (served by `/yadaDataTableData`) and `ytsCustomUserTable` (served by `/test/admin/datatable/userTablePage` with its own policy). The page doesn't render `<yada:datatable>`, whose template needs a `userSession` bean the test application lacks; tests open the page to create the table singletons and read the CSRF meta tag, then post the parameters that DataTables sends. Hibernate SQL is visible to `LogCapture` only after raising the `org.hibernate.SQL` logger to DEBUG.
- The JDK `HttpClient` can fail a request with "header parser received no bytes" when it reuses a keep-alive connection that Tomcat has just closed; `DataTableSecurityIntegrationTest` opens a new client per request and shares only the `CookieManager`.
- `YadaMoney` stores 1/10000 of the currency: `fromDatabaseColumn` takes that internal value, not cents.
- Spring binds a single `sort=property,direction` request parameter to `YadaPageRequest.setSort(List)` as `[property, direction]`; `YadaPageRequest.getPageSort()` joins a lone `asc`/`desc`/`ignorecase` back to the previous element. Two or more `sort` parameters are bound unsplit.
- `YadaSecurityConfig` keeps the Spring Security default response headers plus `Referrer-Policy: same-origin`; HSTS is only written on secure requests, so it never appears over the plain-HTTP test server. Static-resource caching is checked against `/res-<build>/securityheaders/marker.txt` and `/robots.txt` in `src/main/webapp` and a file written at test time under `config.getContentsFolder()`.
- `/ajaxLogin` (the Ajax failure forward of `YadaAuthenticationFailureHandler`) is mapped by `net.yadaframework.tests.web.security.headers.AjaxLoginScenarioController`, whose view shows the failure request attributes.
- The upload-limit fixture (`net.yadaframework.security.uploadtest`, `uploadtest-webapp`) runs with `maxFileUploadSizeBytes` 1024 and counts accepted uploads at `/test/upload/accepted`. Its multipart parse failures other than size (e.g. no boundary) escape the `MultipartFilter` as a container 500.
